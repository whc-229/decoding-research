# 排班 MOEA 本地完整版（脱离前后端，命令行直接运行）

2026-10-13。参照 `../model-crow`（项目软件，前后端结合）重新整理的一份**可在本地直接编译运行**的排班多目标求解程序。
它和服务端走同一条路径，只是去掉了 httplib / SQLite / curl：

```
前端请求 JSON ─→ normalizeRobotSolverParam ─→ 目标 / 全局参数 / MOEA 参数解析
            ─→ para_set_robot_solver：按模板生成 config/1.json…N.json + scenario.json
            ─→ task / properties / Workflows 读入 ─→ MOEA_solver(robot_arrangement_moea) 迭代 ─→ 输出档案
```

## 编译与运行（Linux / WSL；Windows 下用 MinGW-w64 的 g++ 也可编译）

```bash
./build.sh                      # 生成 paiban_dec0（原解码）、paiban_dec1（阈值解码，θ=0.85；THETA=0.9 ./build.sh 可改）、paiban_dec2（阈值+按出勤排序）
./paiban_dec0 --request requests/原请求_paiban.json --workdir work --detail
```

常用参数（未给的一律取请求里的值，与服务端一致）：

| 参数 | 说明 |
|---|---|
| `--pop N` `--gen N` | 种群规模、迭代代数（原请求为 30、10） |
| `--nvar N` 或 `--nvar auto` | 编码长度，默认 auto = 2×⌈任务时长/最短值岗时长⌉（班次数严格上界，见下文）；手动给定时多则截断、少则补足（与修复后的服务端一致） |
| `--graded` `--sim-mutate` `--seed-rule` | 研究用机制（分级惩罚、仿真感知变异、规则播种），见"研究用机制"一节 |
| `--alg NSGA2` | 也支持 MOEAD / IBEA / GREA / HYPE / MOEADD |
| `--objs min_num,max_balance` | 覆盖请求里的目标 |
| `--detail` | 用资源数最少的解再跑一次 `robot_arrangement`，写出甘特数据到 `<workdir>/Res/result.json` |
| `--show-model-log` | 保留目标函数内部的 [DEBUG] 打印（默认屏蔽，否则速度很慢） |
| `--no-auto-types` | 不自动更新 `scenario.json` 的 `objects_type`（服务端行为：沿用模板值） |

输出 `<workdir>/result.json`：档案中各解的目标值与决策变量、每代档案大小、用时。注意 `MOEA_solver` 的档案 EP 里可能混有被支配解和不可行解（目标为 30000），统计时需自行做非支配筛选（`run_compare.py` 已处理）。

批量对比：`python3 run_compare.py 种群 代数 每组次数 进程数 输出前缀`，例如 `python3 run_compare.py 30 10 20 2 prod`。

## 与服务端的差别（只有这些）

1. 不经过 HTTP，直接读请求文件；全局对象（task / properties / Workflows / work_path）在 `main_cli.cpp` 中定义。
2. `scenario.json` 的 `objects_type` 按请求中实际出现的机器人/工具类型数更新（服务端沿用模板值，模板为 1 类机器人、1 类工具；多类型场景必须更新）。可用 `--no-auto-types` 关闭。
3. 求解期间屏蔽目标函数的 [DEBUG] 打印。
4. 甘特结果目录可配置。

## 多类型场景说明（tools/gen_request.py）

机器人/工具的工作流程取自原请求，参数取自毕设 `view.md` 的参数表（一级维修版）：3 类机器人、4 类工具，每类 10 台/件（资源紧场景每类 6 台/件），任务 720 h 或 1440 h。
- `single_work_time` = 去程 + 值岗 + 返程（原请求 G1 为 1+10+1=12）。
- 工具的去程/值岗/返程时长统一取 1/10/1（与原请求相同）。
- **注意**：C++ 按 (类别, 类型, 序号) 定位实体，序号取自 `exampleName` 里的数字，必须在每个类型内从 1 开始编号。

## 发现的问题

1. **（已修复，2026-10-14）基因用完时不检查是否覆盖完任务时长，且没有编码长度预估。**
   原代码的班次循环条件是 `Empty_Time < Cover_Time && i < Nvar/2`，循环结束后不检查 `Empty_Time` 是否达到任务时长；Nvar 完全取前端填写的值（请求里的 `robot_shift` 参数在 C++ 中没有被使用）。实测原请求（700 h）在 Nvar=100 时，返回的"可行解"最后一班值岗在 **502 h** 就结束了。
   修复（三份 `problem.cpp`：算法库 `排班/problem.cpp`、本文件夹、`model-crow/src`）：
   - `robot_arrangement` / `robot_arrangement_moea` 循环结束后加覆盖检查：未覆盖完 → 返回 30000（不可行）；
   - 编码长度按时间轴推进规则计算（不再加经验余量）：第 1 班值岗结束 = 准备时长 + 值岗时长，此后每班值岗紧接上一班，时间轴每班恰好前进所派机器人的值岗时长（值岗节点 "3"）。所以 N 班后已覆盖时长 ≥ N × 最短值岗时长，所需班次数的**严格上界** N_max = ⌈任务时长 / 最短值岗时长⌉，`estimate_robot_nvar()` 返回 Nvar = 2 × N_max（每班 1 个机器人基因 + 1 个工具基因）。`ensure_robot_nvar(Nvar)`：前端给的值多于此数则**截断**（后段基因永远用不到），少于此数则**补足**，并打印说明。原请求：700 h ÷ 10 h → Nvar = 140；三类型 720 h（最短值岗 6 h）→ 240；1440 h → 480。
   - `model-crow/src/algorithm_routes.cpp` 的 3 个排班求解入口（Algorithm_Run、run_robot_moea_solver、单目标排班求解）在构造求解器前调用 `ensure_robot_nvar`；
   - 修改前的 model-crow 文件备份在 `model-crow/backups/pre_coverage_nvar_fix_20261014_*`。
   验证：Nvar=100 且跳过预估（`--allow-short-nvar`，仅测试用）时 15 个解全部被判为不可行；不跳过时补足到 140，代表解覆盖到 702 h。之前的对比实验用的编码长度是 2×(N_max+5)，多出的 10 个基因从不被解码，结论不受影响。
2. 请求中的决策节点名为"判断剩余工时"，而 `standardizeWorkflow` 标准表中的名称是"检查剩余工时"，因此该节点被分配为临时编号 1000。实测充电/维修判断仍然正确（剩余工时 36→24→12→维修 72 h），但若其他代码按编号 "6" 查找该节点会失效。
3. 工具选择 `select_tool = (int)(x * (cargo_type_num - 1))`：可适配工具类型列表中的最后一类只有 x=1 时才会被选中，而上界 Ubound=0.99，因此按这条规则永远选不到最后一类。

## 对比实验结论：原解码 vs 阈值解码（C++ 原模型，NSGA2）

完整表格见 `对比结果_生产档_300次评价.md`、`对比结果_加大档_5000次评价.md`，每次运行的非支配解见对应的 csv 文件。

**生产档（与原请求相同：种群 30 × 10 代 = 300 次评价，每组 20 次）：阈值解码在 4 个场景上全部显著更好（p < 0.001）。**

| 场景 | 最少资源数 均值：原 → 阈值 | 该点均衡度：原 → 阈值 | HV：原 → 阈值 |
|---|---|---|---|
| 原请求（1 类机器人，700 h） | 9.55 → 9.00 | 19.9 → 10.8 | 0.67 → 1.01 |
| 三类型 720 h | 17.1 → 10.2 | 25.2 → 19.1 | 0.76 → 0.95 |
| 三类型 1440 h | 21.1 → 12.8 | 68.4 → 60.5 | 0.70 → 0.89 |
| 三类型资源紧 | 16.5 → 9.8 | 27.6 → 22.6 | 0.71 → 1.00 |

**加大档（种群 100 × 50 代 = 5000 次评价，每组 8 次）：差距明显缩小，原解码在预算充足时也能找到接近最少的资源数。**

| 场景 | 最少资源数 均值：原 → 阈值 | 该点均衡度：原 → 阈值 | HV：原 → 阈值（p） |
|---|---|---|---|
| 原请求 | 9.00 → 9.00 | 7.9 → 6.8 | 0.64 → 0.87（0.13） |
| 三类型 720 h | 9.62 → 9.00（p=0.03） | 12.4 → 9.3 | 0.81 → 0.93（0.32） |
| 三类型 1440 h | 10.0 → 9.0（p<0.001） | 37.8 → 27.1 | 0.87 → 0.95（0.05） |
| 三类型资源紧 | 9.12 → 9.00 | 10.4 → 9.5 | 0.99 → 0.96（0.88） |

**解读：**
1. 阈值解码的主要作用是**加快收敛**。在实际使用的小预算（300 次评价）下优势很大，资源数平均少 0.5–8 个；预算加到 5000 次后，两者的最少资源数基本都到了 9，差距只在最长的 1440 h 场景上仍然显著。
2. 在最少资源这一点上，阈值解码的均衡度在两档预算、全部场景下都更好（均值）。
3. 加大档每组只有 8 次，HV 的差异大多不显著；资源紧场景上两者基本持平。
4. 与 Python 简化仿真（`算法库/排班MOEA_小样例`）的结论方向一致，只是 C++ 原模型在大预算下差距更小。
5. 一次 5000 次评价的运行约需 1–3 分钟（目标函数是逐事件的流程仿真），所以生产环境用小预算，而解码改进恰好在小预算下最有价值。

## 研究用机制（2026-10-14，仅本地研究版；model-crow 未改）

| 机制 | 开关 | 实现位置 |
|---|---|---|
| 排序解码 | 用 `paiban_dec2` | `problem.cpp`：两个评价函数在 `Get_available_Robot` 之后把可用机器人按已出勤班次数升序（同则剩余工时多者优先）排序，再做阈值解码 |
| 分级惩罚 | `--graded` | `main_cli.cpp` 的 `eval_wrapper`：不可行解目标 = 30000 + 1000×(1−已覆盖比例)，原做法一律 30000 |
| 仿真感知变异 | `--sim-mutate` | 新算子 `SIM_MUTATE`（`MOEA_solver::applyVariationOp` 中调用 `custom_op`）替换算子序列中的 `mutate`；按父代的解码轨迹定点改机器人基因：父代不可行→失败班次附近改为复用；可行→一半概率把一次"新开"改为复用、一半概率让出勤最多的机器人让出一个班次；之后再做多项式变异 |
| 规则播种 | `--seed-rule` | `MOEA_solver::seedIndividuals`：初始种群放入全 0 个体（每班复用第一个可用机器人；排序解码下即"最闲优先"）及 9 个小扰动版本，并重建外部档案 |

解码轨迹由 `problem.cpp` 中 `robot_arrangement_moea` 的插桩写入全局 `g_roster_trace`（每班可用机器人数、派出的机器人、新开班次、失败班次、覆盖比例）；`eval_wrapper` 按决策变量的哈希缓存轨迹，供仿真感知变异查父代。结果 JSON 里有评价次数、算子序列、仿真变异调用/命中次数。

**关于 `MOEA_solver` 的算子序列**：`applyVariationOp` 对第 i 个子代只执行序列中第 i mod L 个算子，不是把序列里的算子依次作用在同一个子代上。请求里的序列 `select, crossover, mutate` 中前两个名字没有单独实现，都落到默认的 SBX+PM，所以约 2/3 子代做 SBX+PM、1/3 只对父代副本做 PM。父代池 `pop_sel` 由非支配排序 + 拥挤度截断得到，配对是在其中均匀随机抽取（没有锦标赛）。

批量验证：`python3 run_mech.py 种群 代数 每组次数 进程数 输出前缀`。

## 机制验证结论（C++ 原模型，生产档：种群 30 × 10 代 ≈ 465 次评价，每组 20 次独立运行）

完整表格见 `机制验证_生产档.md`，每次运行的非支配解见 `机制验证明细_生产档*.csv`。基准为阈值解码，检验为 Mann-Whitney。

| 机制 | 结论 | 依据 |
|---|---|---|
| 阈值解码（相对原解码） | **有效** | 4 个场景的最少资源数、HV 全部显著更好 |
| 排序解码（最闲优先） | **有效** | 4 个场景上"最少资源处的均衡度"和 HV 全部显著改善（p ≤ 0.009），最少资源数不变；HV 排名在每个场景都高于阈值解码 |
| 仿真感知变异 | 部分有效 | 单独使用时只在三类型 720 h 显著（最少资源数 p=0.031，HV p=0.007）；在排序解码之上再加，没有额外显著提升（各项 p>0.1） |
| 分级惩罚 | 无作用 | 所有运行都没有出现不可行解，惩罚用不上；只有在资源更紧、容易排不满时才可能起作用 |
| 规则播种 | 有害（就 HV 而言） | 总能拿到最少资源数 9，但均衡度显著变差、HV 显著下降：种群集中到规则解附近，前沿收缩 |
| 全部组合 | 有害 | 比单用阈值解码还差（3 个场景最少资源数或 HV 显著变差），机制之间存在负面交互，主要嫌疑是播种 |
| 排序 + 仿真变异 | 有效（跨场景 HV 排名第一） | 4 个场景均衡度和 HV 全部显著优于阈值解码，但与"阈值+排序"相比无显著差别，增益主要来自排序 |

要点：在真实模型上，有效的改进都集中在**解码器**（阈值解码 + 排序解码）。这与 Python 简化仿真不同：那里排序解码不显著、仿真变异较稳定，说明简化仿真不能替代原模型验证。

## 下界与最优性差距（2026-10-14）

详见 `下界与最优性差距.md`，脚本在 `exact/`。要点：

- 4 个场景的资源数下界都是 9（5 台机器人 + 4 个工具），MOEA 已达到，**差距为 0**。
  - 机器人：4 台在有限时域上被精确搜索证明不可行；
  - 工具：相邻两班的工具必不相同，每班至少带 2 个。
- 资源数 = 9 时的**精确最优均衡度**：原请求 4.019、B 3.386、C 4.406、D 3.386。已用 C++ 原目标函数复核。
  - MOEA 5000 次评价在 9 处的均值是最优的 1.7～6.1 倍；所有运行中最好的一次也是 1.3～1.8 倍。
- 求解方法："前缀分支定界 + 后缀记忆化动态规划"，用时 1～199 s。
  - 用到的结构：出勤周期上限、std 对次数平移不变、相对时间状态。
- 新增 `--eval-genes 基因.json`：逐条调用原目标函数评价给定基因，用于核对和复现。


## 回溯修复解码（2026-10-14 晚）

详见 `回溯修复解码.md`。新增两个解码：

- `paiban_dec4`：维修相位排序，剩余工时少者优先，加容量预判。效果有升有降。
- `paiban_dec5`：出勤少优先排序 + 容量预判 + 回溯修复。某班缺人时，先回溯改派前 12 班中的一班，都不行才新开。

`paiban_dec5` 的效果：
- 相同评价次数下，4 个场景达到资源数下界的比例从 69% 升到 99%，下界层均衡度从最优值的 2.17 倍降到 1.89 倍，有运行找到了精确最优；
- 相同耗时下，仍在最少资源数和 HV 上占优；
- 代价是每次评价约慢一倍。
