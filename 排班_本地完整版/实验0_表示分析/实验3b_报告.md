# 实验 3b：扩充到 64 个实例后的"按实例选解码"（2026-10-15）

## 结论

1. **一个不需要训练的简单选法，在 62 个实例上稳定优于 dec5：按随机样本的最好解选档。**
   - 做法：对每种解码各解码 100 个均匀随机基因，取资源数最少、其次均衡度最好的那个样本；哪种解码的这个样本最好，就用哪种解码跑 MOEA。
   - 候选三档：dec5（逐班基因）、K=0.25、K=0.5（稀疏偏离）。

   | 对照 | 平均 HV 差 | 原 16 个实例 | 新 46 个实例 | 实例层配对检验 | 逐实例显著好/差 |
   |---|---|---|---|---|---|
   | 同评价次数的 dec5（465 次） | **+0.053** | +0.045 | +0.056 | Wilcoxon p = 0.014 | 6/1 |
   | 同总预算的 dec5（20 代，约 765 次，等于 465 + 选档用的 300 次） | +0.039 | +0.031 | +0.042 | p = 0.25，不显著 | 6/2 |

   - 参考上限：事后选最好档 +0.083（偏乐观）；用一半运行选、另一半评价 +0.046。这个简单选法已经接近上限。
   - dec5 把预算加到约 765 次只提升了 0.014。多出的评价次数用来选对解码，比用来多跑几代更划算。不过在同总预算下，它的优势在实例层面还不显著。
2. **学习型选择器（留一实例）没有超过这个简单选法，而且不稳定。**
   - 决策树 +0.025、逻辑回归 +0.037、最近邻 +0.008。
   - 加入 20 代运行后，HV 的归一化随之变化，每个实例的"最好档"标签跟着变，决策树的结果就从 +0.061 掉到了 +0.025。
   - 结论：62 个实例还不够训练可靠的选择器。简单选法本身没有可调参数，更稳健。
3. **这个选法依赖候选集合。**
   - 在实验 3（16 个实例、多一档 K=0.1）中，同样的选法是 −0.032。原因是 K=0.1 最稀疏，随机样本的最好解看起来最好，但留给搜索的自由度太小。
   - 去掉这一档后，选法就有效了。所以候选档本身要有足够的搜索自由度。论文里需要把这一点写成设计原则，并做敏感性分析。
4. **最合适的档在新实例上同样因实例而异。** 62 个实例中 dec5 最好的有 38 个，K=0.25 和 K=0.5 各 12 个。
   - 决策树（全量拟合，只用来看规律）主要用的特征是：K=0.25 的随机最好解比 dec5 的好多少（均衡度、资源数）、两者的初始供给之差。也就是"稀疏编码一开始是否已经比逐班编码好"。

5. **LLM 选档：只读实例描述时选不对；给了随机样本特征后与简单选法打平，但基本是在照抄特征。**
   - 两种提示，每个实例采样 5 次取众数，模型 deepseek-flash，64 个实例全部跑完、无解析失败。评价方式与上表相同（62 个实例）。

   | 方法 | 相对 dec5 | 原 16 / 新 46 | 实例层 p | 逐实例显著好/差 | 选中最好档 | 后悔值 | 选择分布（dec5/0.25/0.5） |
   |---|---|---|---|---|---|---|---|
   | 按随机样本最好解选 | **+0.053** | +0.045 / +0.056 | 0.014 | 6/1 | 0.66 | 0.030 | 36/21/5 |
   | LLM（参数 + 特征） | +0.051 | +0.032 / +0.057 | 0.023 | 6/1 | 0.61 | 0.032 | 32/25/5 |
   | LLM（只给参数） | −0.026 | −0.000 / −0.035 | 0.43 | 4/9 | 0.47 | 0.109 | 31/31/0 |
   | 参考：三档随机选 | −0.072 | | | | | | |
   | 参考：总用 K=0.25 | −0.112 | | | | | | |

   - **只给参数（零评价成本）失败。** 比 dec5 差 0.026，9 个实例显著更差。它只比随机选和总用 K=0.25 好，说明有一点信号，但不够：
     - 它选 dec5 的 32 个实例里，dec5 确实最好的有 22 个（69%）；选 K=0.25 的 30 个里，K=0.25 确实最好的只有 7 个，dec5 反而最好的有 16 个。
     - 分组看：M 组 +0.089（选得好），H 组 −0.043，E 组 −0.163（E 组在 7 个实例上选了 K=0.25，而 E 组的规则离好解远，偏置有害）。
     - 它几乎从不选 K=0.5（0 次），选择和时域长短也没有明显关系。
     - 自己也不确定：5 次采样的众数占比平均只有 0.69，5 次完全一致的实例只占 12.5%。
     - 它的理由大多是"默认规则已经把工作量排得比较均衡，好解应该离规则不远"这类判断。这正是实验 1、2 发现的关键量（规则离好解多远），但光看实例参数判断不出来。
   - **给了特征之后的 +0.051 主要来自特征。** 它和"按随机样本最好解选"有 89% 的实例选择一致；5 次采样众数占比 0.98，92% 的实例 5 次完全一致。和只给参数时相比，两种提示的选择只有 53% 一致。
   - 结论：在这个问题上，LLM 的领域知识不能代替 300 次随机解码给出的信息。给了这些信息后，LLM 也没有比一个无参数的规则多做什么。

**对主线的含义：**
- 方法部分有了一个干净、可复现、无参数的方法：用少量随机采样，在运行前为实例选择编码的偏置和自由度。它有两层支撑：
  - 理论：实验 0～3 中关于偏置与自由度的分析；
  - 实证：62 个实例上同评价次数显著优于 dec5，同总预算下仍有 +0.039。
- LLM 作为选择器没有站住（见第 5 条）：只读实例描述选不对，给了特征后只是在复现简单选法。论文里可以把它作为一个诚实的对照写进去，说明"选对编码需要的信息来自对编码的少量采样，而不是来自对问题的描述"。
- 如果还要给 LLM 找位置，更可能的方向是让它**生成或修改解码规则本身**（比如针对 E 组这类规则离好解远的实例，改写默认规则），而不是在固定的几档之间做选择。

## 1. 设置

- **新实例：** `tools/gen_family2.py` 生成 48 个，E、H、M 各 16 个。规则与原实例族相同，换了随机种子；为控制计算量，1440 h 的时域改为 1080 h。资源数下界用原方法算出，见 `exact/family_bounds2.json`，48 个的机器人下界都是精确值。
- **排除：** E12、E23 两个实例在三档的所有运行里都没有可行解，已排除，所以是 62 个实例。
- **运行：** C++，NSGA2，种群 30 × 10 代，约 465 次评价。新实例每档 5 次；原 16 个实例沿用实验 1～3 的运行（dec5、K=0.25 为 20 次或 8 次，K=0.5 为 12 次或 6 次）。
- **同预算对照：** dec5 跑 20 代，约 765 次评价，64 个实例各 5 次。
- **HV：** 每个实例内用三档和 20 代对照的全部运行统一归一化。
- **特征：** `features8.py`（`FEAT_DEC=dec9`），每档 100 个随机基因，与 MOEA 运行完全独立，不存在信息泄漏。
- **核对：** 重新编译后的 `paiban_dec5` 与 Python 逐解一致（60 条）。K=0.5 在班次上界为奇数的实例上，C++ 和 Python 行为一致（24 条），具体情况见局限。

## 2. 局限

- 新实例每档只跑了 5 次，单个实例的显著性检验功效低；主要看实例层面的配对检验。
- 同总预算按评价次数计。稀疏档每次评价比 dec5 慢约 25%～40%，按耗时计会少一些优势。
- **实现上的一个特殊情况：** 班次上界为奇数时（混合值岗时长的实例），K=0.5 的最后一个偏离槽放不下，默认类型基因会和第 0 班的工具基因共用一位。C++ 和 Python 都是这样处理的，结果一致，但这一点在论文实现时应该修正。
- 每个实例的"最好档"标签依赖 HV 归一化，所以学习型选择器的结论不稳定。
