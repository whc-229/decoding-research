## 解释（2026-10-21）
**机制**：5 条失败规则在第 0、1 班都新开类型 2，第 2 班复用类型 2 时工具不够 → 工具用完。
H13 的类型 2 每班要带 3 件类型 2 工具，这种工具只有 8 件，每件用一次约 23 h 后才能再用（装 2 + 出发 1 + 工作 10 + 返回 1 + 拆 1 + 休息 8）；
连续出勤所需工具 ÷ 可用工具 = 1.12（类型 0、1 为 0.40、0.60）。训练集 15 个实例中这一比值最大只有 0.90（M11_1080h），
所以训练时从未出现"某类型自身效率最好、但工具周转不过来"的情况。

**为什么基因救不回来**：第 0 班（还没有机器人）时各规则首选新开的类型（基因类型 = 0 / 1 / 2）：

| 规则 | 首选新开类型 |
|---|---|
| LLM-full(s2)、LLM-full(s3)、LLM-score(s2)、LLM-score(s3)、EoH(run1) | 2 / 2 / 2（基因不起作用） |
| LLM(r47)、LLM(r35)、默认 | 0 / 1 / 2（照基因） |
| GP(run4) | 2 / 0 / 1 |
| ES16(s0) | 1 / 2 / 0 |

失败规则把"新开哪种类型"从基因手里拿走了；新开类型偏离只在已有机器人容量不够时才生效，而失败发生在第 2～12 班，
约 25% 的偏离槽大多来不及纠正（64 个随机基因只有 0～1 个可行）。r47、r35、GP、ES16 的类型选择随基因变化，只有约 1/3 的基因选到类型 2。

**对应代码**（rulegen/out/<tag>/best_rule.py、neural/out/eoh/run1/best_rule.py）：
- full_s2 `new_candidates`（第 134～173 行）：各类型出勤时长相同（H 组）时走 else 分支，按 `mt/cap + ch/wt − wt/10`（摊到每班的维修 + 充电）排序，
  **该分支没有基因项**；类型 2 得 1.23，类型 0、1 得 2.05、2.08。
- score_s2 `tkey`（第 17～38 行）：按出勤时间占周期的比例 `duties·wt / (duties·cycle + mt)` 排序，基因只加 0.05，已开过的类型加 0.25
  → 第一台开了类型 2 后继续开类型 2。
- full_s3 `new_actions_uniform`（第 155～199 行）：`cost_rate = (cycle + maint/dpm) / w`；score_s3 `new_prefs`（第 118～183 行）：`ct + maint/duties_per_cycle`；
  EoH run1 `type_key`（第 71～138 行）：`busy + maint/cycle_duties`。都是"摊到每班的维修 + 周期"最小者优先，基因不参与或权重很小。
- 根本原因：规则接口 ctx 不提供工具信息（工具由解码器处理；ctx.types 里有机器人的携带件数 carry_num 和可用工具类型 cargo_type_list，但没有工具上限和周转时间），规则无从知道类型 2 的工具不够；
  训练集又没有这种实例，代理分不会惩罚"覆盖基因类型"的写法。
